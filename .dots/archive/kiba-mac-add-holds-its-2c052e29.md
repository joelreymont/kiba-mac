Problem (oracle core 2026-09-25: prior #1 and #6 still open, new High 2; #7 and #8 need their rejection written down): (a) LoginRunner.add runs importLogin (which takes and releases the provider turn) and then Switcher.probe(p, saved, live: false) in a second turn, so a use(saved) queued between them installs the login and the probe then refreshes live tokens. (b) The add snapshots the live Claude item before the Terminal login and LoginRunner.restore writes those bytes back whenever the item differs afterwards; with CLAUDE_CONFIG_DIR set, Claude Code 2.1.282 never writes the live item (it files under paths.loginService), so a difference is the CLI's own token refresh, and writing stale tokens over it can kill the live login. (c) In LoginRunner.run a stop that throws still lets login restore and clear the adding record while the script may still run; and a root removed and recreated lets an old script that already loaded publish its pid into the new root and run the old login. Acceptance: (1) add holds switcher.ops(p) from before the Claude snapshot (Codex: before the login) until after the import and the probe; importLogin and probe become in-turn variants used by add (no re-entry, no second turn); DESIGN Switcher/LoginRunner text says so. (2) restore(old) writes old back only when the live item changed AND the login wrote it: the login wrote the live item only when neither the credentials file nor the login's own item (paths.loginService, compared with before) received bytes; otherwise the live change is the CLI's and stays, and adding is cleared. recover() at start restores only while the login's item is absent. DESIGN step 5/6c updated. (3) A stop that throws leaves the adding record and does not restore (the next start recovers); each add writes a per-run nonce file in root before launch and the script's first line exits unless the nonce file holds its own nonce, so a script from an earlier root never runs in a new one. (4) DESIGN records the rejection of oracle #7 (one LoginRunner per process; the app is one instance, LaunchServices does not launch a second) and of #8 (credentials a login wrote over the live item are only an old CLI's; the redo-able new login is what is lost, never the live one), each in one sentence beside the behaviour. Tests (integration, LoginRunner.add through the fake terminal): one proves a live item changed during the login by a CLI refresh (during: writes new bytes to the live item and to the login's item) keeps the refreshed bytes and saves the login item's; one proves a during-login change to the live item alone (old CLI) is restored and imported (existing behaviour, keep green); one proves the nonce: a stale script cannot publish into a new root (e.g. run the old script text against a recreated root and expect it to exit staleStatus without a pid).
