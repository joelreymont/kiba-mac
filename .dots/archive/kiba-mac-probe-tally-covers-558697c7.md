Problem (oracle UI 2026-09-25: prior #10, #11, #13 still open; new N1, N2, N3, N4, N5), all in Sources/KibaApp/AppModel.swift (Tally, Scope, run, show, report, fail), PanelView.noticeLine, Theme.noticeLines, DESIGN.md AppModel section. (a) #10: Tally.outcome takes its denominator from returned outcomes, so a provider that returns providerError and no accounts drops out and the headline reads 'Usage refreshed for 1 account' over a failed provider. (b) #11/N2: Tally.complete does not check that the report covers the rows the snapshot shows (a row replaced during the probe is not reported; a later status read can add rows), so 'All usage probed' can stand over uncovered rows and apply keeps a complete run after new rows appear. (c) #13/N1: show(.autoProbe) assigns probeNote/probeError from the auto-probe's outcome, so a held note (e.g. an account removed by the last manual probe) vanishes on reopen although DESIGN says the opening probe supersedes nothing. (d) N5: show's changed comparison looks only at held fields, so a first-time 'waiting for its CLI' outcome is never announced. (e) N3: noticeLine caps the notice at three lines and a report with three or more account details is cut with no way to read it. (f) N4: an error reported during a running action (report/fail from the status menu's login-item toggle) is erased when the action completes and show(.action) assigns its empty errors. Acceptance: (1) the denominator is the number of rows the snapshot shows for every provider; a provider whose report has providerError and no accounts counts all its rows as not refreshed and the headline says so. (2) A run is complete only when every row in the reconciled snapshot has a recorded outcome in the report; rows added or replaced since make it incomplete ('Some usage probed'); lastProbe reflects that after apply. (3) The auto-probe merges: it keeps every held line and fault from before and adds its own (deduplicated), and announces only what is new. (4) Announcement dedup compares the announcement text, so a new waiting outcome is announced once and its explanation is held (not faded) until a user action supersedes it. (5) The notice grows with its content inside the panel's capped scroll view (no lineLimit cap on held details); DESIGN's three-line rule becomes 'the notice shows whole'. (6) Errors reported during an action are merged into that action's completion errors, never erased by it. Tests (integration through AppModel with the stub backend, as appModelCountsProbeResults does): each of (1)–(4) and (6) has a test that fails before and passes after; (5) is a view rule, documented.
